# M27 开发笔记 · MCP elicitation：确认门升级为真弹窗

M22 的 MCP 确认门是"环境变量决断"：stdio 场景没有前端，`PAPER_AGENT_CONFIRM`
默认 approve，人类并不在环。P3 目标：支持 elicitation 的宿主（如 Claude
Desktop）在 `add_papers` / `run_code` 触发确认门时弹**真实确认界面**，人点
确认/拒绝后执行才继续；环境变量降级为运维开关与老宿主逃生口。

## 1. SDK 2.2 探明：input_required 多轮往返流

先读源码再动手（SDK 2.2 的 elicitation 面和 1.x 完全不同）：

- `on_call_tool` 的返回类型是 `CallToolResult | InputRequiredResult`——工具
  调用可以**不完成**，先返回 `InputRequiredResult(input_requests=…,
  request_state=…)`；
- `input_requests` 是 `dict[str, CreateMessageRequest | ListRootsRequest |
  ElicitRequest]`，宿主把内嵌请求分发给自己的回调表（ElicitRequest →
  elicitation 弹窗 UI）；
- 宿主补完输入后**重试原请求**：`tools/call` 参数自带 `input_responses` +
  `request_state`（原样回传）两个字段，服务端拿到人的决定后重新执行；
- 客户端默认 `allow_input_required=False` 会把这种结果当异常——这是给
  host 驱动的契约，不是给模型的。

选型：**不用老式 `elicitation/create` 中途 RPC**。那条路要把同步 confirm
回调（跑在 `to_thread` 工作线程里）桥接回异步请求上下文再挂起等待——
`anyio.from_thread.run` 能做，但服务端要挂住一个执行中的请求等人在别处点
按钮；input_required 流把"等待"交还给协议层的往返，服务端保持无状态，
两次调用之间什么都不用存（request_state 由客户端义务性回传）。

## 2. 连接时代：initialize 握手 vs discover

第二个坑：协议版本协商。`ClientSession.initialize` 发起的握手**只协商
legacy 版本**（最高 2025-11-25），而 `InputRequiredResult` 是 2026-07-28
词汇——legacy 连接上序列化直接报 "Handler returned an invalid result"
（按当次协商版本的 union 校验，tools/call 结果只认 CallToolResult）。
现代连接走 `server/discover`：客户端提议最新版本，双方取交集后
`adopt()`。测试助手从 `initialize()` 换成 `discover()` 后才通过；同时
保留一条 legacy 用例覆盖老宿主路径（老宿主 + env 兜底）。

## 3. 服务端实现（mcp_server.py）

confirm 回调三段优先级（`confirm_gate`）：

1. `PAPER_AGENT_CONFIRM=approve|reject` 显式设置 → 直接决断。运维开关 +
   不支持 input_required 的老宿主逃生口，每次写 stderr 审计；
2. 未设置且本次请求没有 `input_responses` → 抛 `_NeedUserInput`，
   `_run_tool` 捕获后返回 `InputRequiredResult`（内嵌 form 模式
   elicitation：消息 + approve 布尔表单 + `request_state`）；
3. 重试带响应 → `accept` 放行；`decline`/`cancel`/响应键缺失一律拒绝
   （失败关闭）；表单里 `approve=false` 即便 action=accept 也否决——
   尊重表单内容而非只看提交动作。

两个关键机制：

- **request_state 归属校验**：打包 `{tool, arguments}` 下发，重试时核对
  `state.tool == 本次工具`，缺失或对不上 → fatal（"拒绝套用人工确认
  响应"）。响应必须归属本工具的待确认请求，防止错配；
- **`_NeedUserInput(BaseException)`**：这是本项目最隐蔽的坑。最初继承
  `Exception`，测试里 confirm 抛出后客户端收到的是 degraded——排查发现
  异常根本没离开 `ToolExecutor.execute`：`run_tool` 四态分类器的
  `except Exception` 把它吞成了 `[unexpected] degraded`（M22 语义下
  confirm 从不抛异常，这条路径从没被走过）。改成 BaseException 子类
  （与 `asyncio.CancelledError` 同类）：协议层控制流信号必须穿透工具层
  的异常分类，`_run_tool` 就地接住，不外泄。

`input_responses` 的传递用 contextvar：confirm 回调跑在工作线程，
`_blocking` 里 `set` / `finally reset`——随线程上下文到达回调，不挂在
executor 单例上（否则请求间串味）。

## 4. 测试与真机验证

- MCP 测试 5→10：accept 全回路（首触断言 result_type/mode/消息，重试后
  run_code 真执行 exit 0 + stdout）、decline 语义（协议成功但 declined，
  模型可理解，非 is_error）、伪造 request_state → fatal、env=reject 跳过
  往返、gate 单元（无响应抛 `_NeedUserInput` / 各 action / approve=false
  否决 / 空响应字典失败关闭）；legacy initialize 路径保留；
- 全量 222 用例通过（217 + 5）；
- 真实 stdio 冒烟：spawn `pa mcp` 子进程 → discover 协商到 2026-07-28 →
  library_status → write_code/run_code 首触升级 input_required → accept
  重试 → exit 0 + stdout 正确，stderr 两阶段审计齐全，冒烟文件清理。

## 5. 面试知识点

- **input_required vs 中途 elicitation RPC**：前者把交互等待建模为协议
  往返（无状态服务端、宿主驱动重试），后者是请求中途的 server→client
  调用（需要上下文桥接与挂起）。工具类 HITL 优先前者；
- **控制流异常为什么用 BaseException**：`except Exception` 兜底分类器
  （四态映射）会吞掉业务控制流；CancelledError/GeneratorExit 同理。代价
  是它不会被任何通用兜底捕获——必须由发起方保证就地接住；
- **协议版本协商的双轨制**：initialize 握手（legacy ≤2025-11-25）与
  server/discover（2026-07-28 现代词汇）是两条升级路径，写协议适配层要
  先确认连接时代再决定可用的结果形状。
