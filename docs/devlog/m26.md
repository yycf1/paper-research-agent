# M26 开发笔记 · 任务锚定与工具作用域：漂移事故的系统性修复

M25 的漂移事故（续任务未锚定 source_id → 模型自行检索、入库另一篇论文、
在别人的工作区写代码）暴露了一个结构性问题：**"专注本论文"只活在任务
文本里，而 prompt 约束只是建议**。M26 把它升级为代码强制——这是本项目
护栏哲学（熔断→纠偏→拒绝）在"任务上下文"维度上的延伸。

## 1. 设计：两层防御 + 一个产品入口

- **约束注入（循环层）**：任务 API 新增 `anchor_source_id`，循环层把锚定
  约束写进系统提示（锚定论文 id、禁止更换研究对象）；
- **工具作用域（执行器）**：锚定任务的工具面直接**移除** search_papers /
  add_papers / explore_directions（M25 事故的直接肇因）——模型看不到就不
  会调用，比调用后再拒绝省一步；`execute` 侧保留同判定（防御纵深），
  万一被调用返回 fatal 并说明原因，供模型自行修正方向；
- **产品入口**：详情页「复现」页签新增「🤖 交给 Agent 续做（锚定本论文）」
  ——一键把模板任务 + 锚定 id 跨页传入助手页（预填不自动运行，用户确认
  后执行），输入框上方显示锚定提示条。锚只随本次提交走，提交后清除，
  不污染下一个无关任务；
- CLI 同步：`pa agent --anchor <id>`（复用 `_resolve_sid` 的 id 片段解析，
  锚定不存在的论文直接 404，任务不启动）。

## 2. 为什么是"隐藏"而不只是"拒绝"

工具面裁剪在 `specs_for()`（循环层取工具清单处）生效：锚定任务的模型
**看不到**作用域外工具。这是最小权限原则的工具版——权限不靠模型自觉，
靠"根本不在菜单上"。拒绝路径仍然保留，因为轨迹回放/未来动态作用域下
执行器可能被直接调到。

## 3. run_code 可观测性：-u 无缓冲

M25 的"150s 超时 + 空 stdout"是块缓冲假象（杀进程丢缓冲）。子进程改为
`python -u`：超时时已打印的内容都能从管道读到。配回归测试：脚本无
flush 打印后 sleep，超时结果 stdout 必须包含该行（修复前为空）。

## 4. 验证

- 新增 `tests/test_agent_anchor.py` 4 用例：作用域裁剪（specs_for 排除 +
  execute fatal 带锚定说明）、无锚定时工具面完整、循环层注入断言（假模型
  捕获 system 与 tools）、run_code -u 超时捕获输出；
- `test_api_agent.py` +2：锚定不存在论文 404；端到端——锚定任务里模型
  调 search_papers 被执行器拒绝（step fatal + 锚定说明），任务继续收尾，
  state.anchor 记录在案；
- 真机端到端：详情页按钮 → 预填 + 锚定提示条 → 提交 → 9 步全部在作用域
  内（read_repro_plan + library_status + 4 写 3 跑自纠错循环）→ **零漂移**
  → 8 步熔断软着陆，输出工作区状态诊断与下一步建议；
- 全量回归 217 通过。

## 5. 面试视角

- **prompt 约束 vs 代码强制的边界**：模型的"自觉"用于策略选择，护栏
  必须在代码里——锚定把一次真实事故转成了三条防御（注入提示、工具面
  裁剪、执行拦截）；
- **最小权限工具集**：动态按任务类型裁剪工具面，是多工具 Agent 的通用
  模式（同 MCP 场景下按 host 需求暴露子集同理）；
- **上下文锚定的产品化**：锚定信息应该由任务发起方（UI/CLI）显式携带，
  而不是指望模型"记得上一轮"——无记忆是多任务 Agent 的默认假设，
  设计要围绕它展开。
