# M14 开发笔记 · Function-calling Agent Loop

把 M5 备好的工具契约地基（TOOL_REGISTRY + 四态 ToolResult）真正盖上房子：
**LLM 在循环里自主决定调什么工具、调几轮**，控制流从 Python 硬编码转移到模型手里。

## 1. 两种范式的分界

此前 `pa chat` 是「路由模式」：`classify_intent` 一次 LLM 调用产出意图 + 参数
JSON，之后的检索/问答/状态分发全是 Python 写死的路径——LLM 看不到工具结果，
一步走完就结束，多步任务（先检索再入库再追问）编排不了。

M14 的「循环模式」核心协议只有三句话：
1. assistant 消息声明 `tool_calls`（工具名 + 原始 JSON 参数），**必须原样回进上下文**；
2. 每个调用的结果以 `role=tool` 消息回填，靠 `tool_call_id` 与调用一一配对；
3. 模型看到结果继续决策，直到不再发起 `tool_calls`（即最终回答）。

实测 GLM-4.7 的 OpenAI 兼容端点完整支持该协议（探针一次通过）。

## 2. 关键决策

- **llm.py 重构而非并列**：`chat()` 退化为 `chat_with_tools()` 的文本包装，
  两者共用 `_complete()` 限流重试核心；`getattr(msg, "tool_calls", None)` 兜底，
  存量 143 个测试零改动通过。
- **检索词不再过查询优化器**：`search_papers` 工具内部 `raw=True`——agent 自己
  负责英文检索词构造，省一次 LLM 调用；M5 的查询优化器继续服务无 agent 的
  `pa search` / `pa chat` 路径。
- **预览与入库拆成两个工具**：`search_papers` 只读不写，`add_papers` 按序号
  （"1,3-5"/all）入库。候选暂存在执行器实例里、模型只引用序号——避免论文
  JSON 在轮次间搬运挤占上下文，也把「哪些值得入库」变成模型的真实决策点。
- **错误回填而非抛出**：工具失败按四态语义进 `role=tool` 消息（fatal 带可用
  工具清单，degraded 带原因），模型可换参数重试或如实告知用户；LLM 层故障
  才转成 `stopped_reason=error` 的结果对象。
- **步数熔断软着陆**：触达 `max_steps` 后追加一条 user 消息禁用工具再调一次
  （`tools=[]`），让模型基于已有信息收尾，而不是硬报错。
- **thinking=False**：循环内「选工具、填参数」属简单任务，沿用 M5 教训——
  GLM 混合推理模型的思考 tokens 会吃光 max_tokens 导致 tool_calls 为空。

## 3. 踩坑与观察

- Windows 控制台 GBK 环境跑探针/CLI 必须 `python -X utf8`，否则中文输出崩；
- 真实多步冒烟：`pa agent "检索 2024 年后 GNN 推荐论文并评估价值"` 一步
  search_papers（27s，瓶颈仍是数据源网络）后模型产出结构化推荐，甚至识别出
  一篇 RETRACTED 论文建议避开——工具结果质量直接决定 agent 判断质量；
- 步数与 token 的关系是线性的：每一步都重放全部历史消息，8 步循环的上下文
  膨胀要靠 tool 消息截断（4000 字符）与候选封顶（30 条）双重保护。
