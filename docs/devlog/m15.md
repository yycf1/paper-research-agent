# M15 开发笔记 · Agent 护栏硬化与评测体系

回答一个尖锐的问题：**「你的 agent 防得住死循环吗？敢让它碰危险操作吗？」**
M14 的回答是"有 max_steps 兜底"；M15 的回答必须是"四道代码强制护栏 + 可量化评测"。

## 1. 护栏四件套（loop/executor 层，全是代码强制而非 prompt 建议）

**循环检测器**（`agent/loop.py::_RepeatGuard`）：agent 死循环的最常见形态是
同参数重复调用同一工具。签名 = (工具名, 参数 JSON 按键排序序列化)，第 2 次
放行执行但回填 `warning` 字段（"重复调用不会产生新结果"），第 3 次**直接拒绝
执行**——不触碰真实工具，回填 fatal。关键取舍：不是第 2 次就拦（同参数重试
可能是数据源瞬态故障，给一次机会），也不是无限宽容（每步都烧 token）。

**token 预算**：max_steps 限步数但限不了成本——每步重放全部历史，上下文
递增。预算闸在**每轮 LLM 调用前**检查累计用量（`prompt+completion`），超限
即 break 进软着陆（与步数熔断共用"禁止工具、强制总结"的收尾路径），
`stopped_reason=token_budget`。默认 120k，config.yaml `agent.token_budget`。

**入库上限 + HITL 确认钩子**：`add_papers` 单次超 `add_cap`（默认 20）直接
fatal 拒绝并教模型分批——**拒绝而非静默截断**，截断会让模型误以为全部入库。
达 `confirm_threshold`（默认 5）触发 `confirm(count, titles) -> bool` 钩子：
CLI 接 typer.confirm 交互，评测传 None 自动放行。这是为未来删除/下载/执行类
危险工具预装的通用插座——届时同一钩子签名单点接入。

**retryable_error 语义落地**：M5 四态契约里的 `retryable_error` 一直是死代码
（HTTP 层内部重试，失败直达 degraded），agent 无法区分"该重试"和"该换路"。
`run_tool` 现在按错误消息里的限流特征（`429|rate.?limit|too many requests`）
分类：限流 → `retryable_error(retry_after=15)`，循环层**自动 sleep 重试一次**
（对模型无感，步骤详情标注"自动重试后"）；其余源故障仍是 degraded 交模型换路。
职责划分清晰了：**暂时性失败框架扛，结构性失败交模型**。

**软着陆文案统一**：max_steps 与 token_budget 触顶共用收尾路径，stopped_reason
区分原因，CLI 按 reason 渲染不同警告。

## 2. 评测体系（回应「召回率 100% 是红灯」）

**检索排序指标**（`rag/eval.py`）：hit@k 曲线（1/3/5/8）+ MRR + nDCG@8。
二值相关性下 nDCG 的理想 DCG 按 top-k 内实际召回的相关块数近似（全库相关
总数不可廉价获得，文档化在 docstring）。`pa eval --report` 输出明细表 + 聚合。
口径注意：scope-01（范围外诚实拒绝用例）无期望出处，不进排序指标分母。
实测数字见 §4。

**Agent 任务评测**（`agent/eval_agent.py` + `eval/agent_tasks.json`）：
10 任务 × 3 类能力面（single_tool / multi_step / boundary），判定三维：
- completed：stopped_reason=final 且答案非空；
- tool_ok：must_call ⊆ 实际调用 且 forbidden ∩ 实际调用 = ∅——
  **越界操作（boundary 任务调了工具）是硬红线，违规数必须为 0**；
- answer_ok：关键词组（组间 AND、组内 OR，复用 RAG 评测同一判定）。
成本指标：平均步数 / 平均 tokens。判定全部纯函数离线测试，runner 只注入
executor 工厂与 chat_fn；`pa eval-agent --trace` 每任务轨迹落盘。

## 3. 工程细节

- 轨迹 JSONL 逐步 flush 写（`_TraceWriter`），中途崩溃也能复盘已发生步骤；
  `pa agent --trace` 存 `data/traces/agent-<时间戳>.jsonl`。
- Windows 控制台 GBK 坑再确认：CLI/探针一律 `python -X utf8`；
  管道后接 findstr 匹配中文会因编码错位失败，重定向到文件再读更稳。
- 测试侧：脚手架假模型的脚本耗尽/`tools=[]` 收尾调用统一回兜底最终回答，
  测试聚焦循环协议本身（消息回填顺序、tool_call_id 配对、签名拦截时机）。

## 4. 实测数字与改进闭环（eval → fix → re-eval）

首轮 `pa eval-agent`（10 任务）：完成率 90%，平均 2.5 步 / 6161 tokens。
唯一失败 `search-add-01` 的轨迹复盘出一条完整失败链：

1. 三源真实故障（OpenAlex 429 / arXiv 超时 / EuropePMC 503）；
2. `search_papers` 却返回 `ok + 0 结果`——「源挂了」与「没论文」混为一谈，
   模型无从判断，只能换词重搜（8 次变体，恰好绕过只拦完全同签名的检测器）；
3. 第 4 步实际命中 15 篇新候选，模型未推进 add_papers，撞步数熔断收尾，
   且总结误报「全部失败」（未编造，诚实兜底生效）。

针对性修复：① `search_sources` 结构化暴露 `degraded_sources`，全源故障时
工具结果带显式 `warning`（0 结果大概率是故障，不要重搜，如实汇报）；
② 循环检测器加工具级计数（同工具第 4 次起注入推进提醒），补变体循环盲区。

复测：**完成率 90%→100%，平均 2.5→1.9 步，平均 tokens 6161→5240**。
同样的全源故障下，模型 2 步即识别故障并诚实汇报（search-add-01 从 18.9k
tokens 降到 4.3k）。剩余的 tool_ok ✗ 是评测判定器设计问题：任务 must_call
无条件要求 add_papers，但源全挂时「不入库、如实汇报」才是正确行为——
条件期望（有候选才要求入库）是判定器的待办，属于评测设计教训：
**依赖活数据源的评测天然有方差，判定器必须区分「没做到」与「不该做」。**

检索侧首轮 `pa eval --report`（25 条带期望出处 case）：hit@1 52% / hit@3 76% /
hit@5 88% / hit@8 100% / MRR 0.665 / nDCG@8 0.727——"100% 命中"的真相是
近半数 case 的相关块排不到第一，排序劣化从此有数字可抓。

## 5. 已知边界（诚实记录）

- 循环检测签名级只拦"完全同参数"，工具级第 4 次起是提醒不是硬拦——
  最终仍由 max_steps/token_budget 兜底；
- nDCG 的理想 DCG 按 top-k 内实际召回的相关块数近似（全库相关总数不可廉价
  获得），跨系统对比时需核对口径；
- boundary-ambiguous 的答案判定依赖模型反问措辞，偶发误判可能；
- agent 任务评测依赖活数据源，结果有运行间方差，README 报告两轮数字。
