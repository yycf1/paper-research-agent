# M23 开发笔记 · 任务中心：历史回读 + SSE 推送

承接 M21 的收尾讨论：Agent 任务此前是一次性视图——只有最近一次、刷新即失；
前端每 1.2s 轮询一次任务状态。M23 两件事：把任务变成**跨会话资产**（历史
列表 + 轨迹回读），把轮询换成 **SSE 推送**；顺带把库页失败行的裸报错收敛
成可读文案。

## 1. 历史的真实来源：轨迹文件，而不是第二份存储

任务注册表在内存里（重启即失），但 M16 起每次任务都落了 JSONL 轨迹——
历史功能的正确做法是**回读已有产物**，不引入第二份存储：

- 轨迹文件名从 `时间戳.jsonl` 改为 `时间戳-<task_id>.jsonl`：任务 id 由
  routes 预生成，同一 id 同时进内存注册表与磁盘文件名——这是重启后
  「live 条目 → 历史条目」无缝衔接的关联键；旧文件（无 id 命名）用整个
  stem 当 id，兼容不迁移；
- `GET /agent/tasks`：内存注册表（live 优先）+ 轨迹目录扫描，按 id 去重，
  新→旧。轨迹解析出 task/step/final 三种记录；**缺 final 记录 = 进程中断**，
  如实标为 error（"轨迹缺少最终记录"），不伪装完成；
- `GET /agent/tasks/{id}`：注册表未命中时按 id 回读轨迹（含全部步骤），
  前端时间线原样重建——M16 的"服务重启后 404"就此消失。

逐步追加写的轨迹设计在这里兑现：中途崩溃也能复盘到已发生的步骤。

## 2. SSE：同进程共享状态，推送替代轮询

`GET /agent/tasks/{id}/events`（text/event-stream）：

- 连接即推 `snapshot`（全量状态，含已有步骤）；此后循环检测共享状态对象
  的增量——新步骤逐条推 `step`，状态变化推 `status`（含 answer/usage/
  pending_confirm），终态后推 `end` 并收流；
- **不需要事件总线**：任务线程与 SSE 生成器在同一进程，共享同一个
  `AgentTaskState` dict（M18 的原地更新机制），生成器只负责"观察差异"；
- 同步侧 sleep 0.4s 是进程内检查，对比轮询方案省掉了每连接每 1.2s 的
  HTTP 往返与 JSON 序列化，延迟从"平均 0.6s"降到毫秒级；
- 前端 `EventSource`：断流（代理缓冲/服务重启）onerror 回退到轮询兜底，
  UI 不冻结；确认门 POST /confirm 后由下一条 status 事件自然推进。

## 3. 错误文案：表格里的原始报错收敛为一句话

失败行此前裸奔 `https://europepmc.org/...pdf=render -> HTTP 403`。加
`fmtError`：HTTP 状态码映射为「源站拒绝访问（403）」等短语，超时/非 PDF
内容各归其类，兜底截断 64 字符；完整报错保留在 title 悬停提示——摘要给
扫视，细节给排查。

## 4. 验证

- 测试（`test_api_agent.py` 7 用例）：新增历史回读（清空注册表模拟重启 →
  列表与详情从轨迹重建，404 兜底）、SSE 快照即终态、SSE 增量（用
  threading.Event 卡住第 2 步造 running 窗口，验证 step/status 事件序列
  到 end 收尾）；
- 真机：历史面板渲染 6 条（5 条旧轨迹 + 1 条 live）；点击即重建时间线；
  提交新任务后 performance 资源记录只有 **1 条 /events 连接、0 条轮询
  GET**，步骤与答案实时呈现；失败行显示「源站拒绝访问（403）」、悬停见
  原始 URL；全量回归 207 通过。
- 文案修正一处：live 不等于"进行中"——只有 running/waiting_confirm 才标。

## 5. 面试视角

- **不造第二份存储**：历史功能的第一反应可能是"加张表"，但轨迹 JSONL
  已经是完整事实源——回读它，live/历史的唯一区别是注册表里有没有；
- **SSE vs 轮询的本质**：不是"新技术替代旧技术"，而是当状态源与推送端
  同进程时，轮询的 HTTP 往返完全是浪费；跨进程/跨机时才需要真正的
  消息通道（Redis pub/sub、消息队列）；
- **事件流的消息设计**：snapshot + 增量 + 终态信号（end），是所有实时
  订阅协议（SSE/WebSocket/gRPC stream）通用的三段式。
